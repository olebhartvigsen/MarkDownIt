# ELK layered port: an oracle first

## Why

The app lays Mermaid flowcharts out with an ELK-shaped profile over the
engine in `src/mermaid/`. That engine is a dagre port whose golden gate
holds it to dagre-d3-es geometry, and since the default moved to ELK the
goldens no longer describe what ships. A property suite
(`tests/mermaid_elk_fixtures_test.cpp`) covers the shipped profile, but a
property is not a reference: it cannot tell a slightly wrong placement
from a right one.

The only honest reference for an ELK layout is ELK. That means porting
ELK's layered algorithm well enough that its own numbers can be recorded
once and compared for years.

## Hard constraint

ELK is Java (elkjs is JavaScript). The app ships neither runtime, and it
never will: the Mermaid renderer is native and offline by design. elkjs
is therefore a **development and CI tool only**, living in
`tools/elk-oracle/`, exactly like `tools/mermaid-oracle/` is today.

## Method

1. `FlowchartToLayoutGraph` builds the graph with the app's own node
   sizes, so a difference in the output is a difference in layout and
   never in measurement.
2. `tools/elk-oracle/elk_oracle.mjs` lays that graph out with elkjs using
   the settings the app uses (`spacing.nodeNode` 20,
   `nodeNodeBetweenLayers` 20, `edgeNode` 10, `edgeEdge` 10, padding 12,
   `NETWORK_SIMPLEX`, `BRANDES_KOEPF`, `GREEDY`, `ORTHOGONAL`,
   `NODES_AND_EDGES`), and writes the geometry in the golden JSON shape.
3. Goldens land in `tests/mermaid/golden-elk/`, generated, never edited.
4. The port is judged against them: node centres, then edge routes.

The graph dump is a throwaway for now and becomes a CMake target beside
`layout-parity` once there is something to compare in CI.

## Where the engine stands

Measured against real ELK on the nine chart fixtures (node centres,
points):

| fixture | max Δx | max Δy | avg Δx | avg Δy |
|---|---|---|---|---|
| 01-linear | 0.0 | 0.0 | 0.0 | 0.0 |
| 02-shapes-edges | 14.9 | 267.0 | 9.9 | 232.0 |
| 03-diamond | 24.7 | 0.0 | 12.3 | 0.0 |
| 04-crossing | 74.0 | 20.0 | 37.0 | 10.0 |
| 05-long-edge | 11.2 | 0.0 | 8.4 | 0.0 |
| 06-siblings | 53.0 | 10.0 | 13.2 | 7.5 |
| 07-lr | 0.0 | 0.0 | 0.0 | 0.0 |
| 08-rl | 0.0 | 0.0 | 0.0 | 0.0 |
| 09-bt | 0.0 | 0.0 | 0.0 | 0.0 |

So: direction handling, layering and the spacing model already agree
with ELK exactly on straight charts in all four directions. What does not
agree is where siblings and crossings are ordered, which is the crossing
minimisation and the Brandes-Koepf alignment, not the spacing.

`02-shapes-edges` differs in y by hundreds, which is a different problem:
rank assignment around shapes and self loops, not ordering. It is the
first thing to understand, because a 267 pt difference is not a tuning
delta.

## Phases

1. **Oracle (done).** elkjs, settings, nine fixtures, goldens committed.
2. **Understand the 267.** Find out whether ELK ranks self loops and
   shape nodes differently, and whether our fixture graph is the same
   graph ELK saw. No code change until the difference is explained.
3. **Ordering.** Move crossing minimisation and the coordinate
   assignment to ELK's rules (median/barycenter sweeps with ELK's
   tie-breaking, then its Brandes-Koepf alignment bands).
4. **Routing.** ELK's orthogonal routing along the dummy chains, with
   its edge-node and edge-edge spacings applied separately.
5. **Wire the gate.** A CI job runs the oracle and diffs the goldens, and
   the port is compared to them with a tolerance that starts loose and
   tightens only when a fixture earns it.
6. **Then, and only then,** the dagre goldens can be retired or kept as
   the fallback profile's reference.

## Rules

- Goldens are generated by ELK and never hand-edited.
- A fixture that cannot be matched is a row in this document with the
  reason, not a tolerance raised quietly.
- No JS runtime is added to the app. If a change cannot be expressed in
  C++, the port stops there.
