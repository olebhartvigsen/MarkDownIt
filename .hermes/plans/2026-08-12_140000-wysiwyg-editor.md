# MarkDownIt WYSIWYG Editor Implementation Plan

> **For Hermes:** Use subagent-driven-development to implement this plan
> task by task. Use `wsl-windows-native-dev` for the build-swap-verify loop.
> CI (windows-2022) is the only compile gate. Write C++ via base64 through
> `execute_code`, never `write_file`.

**Goal:** Turn MarkDownIt from a read-only viewer into a true WYSIWYG editor
where the user types directly into the rendered layout, sees formatting
applied live, and never has to look at markdown syntax.

**Architecture:** Keep the single-exe, zero-dependency Win32 and Direct2D
stack. Add an editable document model with stable source offsets, a caret
and selection layer, a text input pipeline, an incremental re-parse loop,
and a serializer back to markdown. The renderer stays the single source of
visual truth; the editor writes into the model and asks the renderer to
redraw.

**Tech Stack:** C++17, Win32, Direct2D, DirectWrite, md4c (already vendored),
plus the Windows Text Services Framework for IME support.

### What blocks editing today

1. **No source offsets.** `Node` and `InlineBlock` carry text but no link
   back to byte ranges in the original file. Editing needs that link to
   round-trip text without losing the user's own markdown.
2. **Layouts are transient.** `Render` calls `CreateTextLayout` per block
   per frame and releases it immediately. Hit testing a mouse click to a
   character requires keeping those layouts alive between frames.
3. **No caret, no selection, no focus.** The content window never calls
   `CreateCaret`, never handles `WM_CHAR`, and does not take keyboard focus.
4. **Full reparse on every load.** `LoadFile` reparses the whole buffer.
   At one keystroke per reparse that is fine up to a few hundred KB, but
   the layout cache must be invalidated surgically or typing will stutter.
5. **No undo history.** Nothing records what changed.
6. **Rendering is stateless top-to-bottom.** `curY` accumulates as it draws.
   Nothing records where each block landed, so a click cannot be mapped
   back to a block.

## Design decision: which WYSIWYG model

Three approaches exist. This plan picks the third.

**Option A: rich-text model, markdown only on export.** The document becomes
a styled-run tree. Markdown is generated on save. Cleanest editing story,
but it destroys the user's original markdown formatting on every save, and
round-tripping arbitrary markdown is lossy. Rejected.

**Option B: source-of-truth markdown, render-only preview.** What the app
does now, plus a text pane. That is a split-pane editor, not WYSIWYG.
Rejected because it contradicts the stated goal.

**Option C: markdown as source of truth, edits applied as text splices,
layout regenerated from the parse.** The user sees only the rendered view.
Keystrokes translate into splices on the underlying markdown buffer. The
document reparses, the layout rebuilds, the caret is restored by source
offset. This keeps markdown lossless, keeps md4c authoritative, and gives
true WYSIWYG. **Chosen.**

The cost of Option C is that every edit reparses. Task 12 addresses that
with block-level incremental parsing.

## Libraries needed

Nothing new needs to ship. The three additions are all Windows components
already present on every Windows 10 and 11 machine.

| Library | Purpose | How it ships | Link flag |
|---------|---------|--------------|-----------|
| md4c 0.5.3 | already vendored, stays the parser | source in `third_party/` | none |
| Text Services Framework | IME composition for CJK and emoji | `msctf.dll`, in-box | `-lmsctf` |
| Uniscribe or DirectWrite | already used, gains hit testing | in-box | already linked |
| Windows Clipboard API | copy, cut, paste | `user32` | already linked |
| RichEdit (optional) | **not used**, listed to explain why | n/a | n/a |

RichEdit is deliberately avoided. Hosting a RichEdit control would mean two
competing layout engines and would break the Direct2D typography work
already done. The editor is built on DirectWrite hit testing instead.

**One optional third-party library is worth considering:**

| Library | Purpose | License | Verdict |
|---------|---------|---------|---------|
| ICU (in-box since Win10 1703) | grapheme cluster breaking | ICU | Use `icu.dll` via `<icu.h>`. Needed so arrow keys step over emoji and combining marks correctly rather than splitting them. |

`icu.dll` ships with Windows 10 1703 and later. Guard the calls so the app
degrades to naive UTF-16 stepping on older builds rather than failing to
start.

## Architecture: the five new subsystems

```
                 keystroke / mouse
                        |
                        v
              +-------------------+
              |   EditController   |  Task 6, 7, 8
              +-------------------+
                        |
              splice(offset, len, text)
                        v
              +-------------------+
              |    TextBuffer      |  Task 2
              |  (UTF-8 markdown)  |
              +-------------------+
                        |
                  dirty range
                        v
              +-------------------+
              |  IncrementalParse  |  Task 12
              +-------------------+
                        |
                    Document
                        v
              +-------------------+
              |   LayoutCache      |  Task 4
              | (live TextLayouts) |
              +-------------------+
                        |
                        v
              +-------------------+
              |     Renderer       |  existing
              +-------------------+
```

`TextBuffer` owns the markdown. `Document` is derived state. `LayoutCache`
is derived from `Document`. Nothing ever writes to `Document` directly.

### Task 2: Create the TextBuffer

**Objective:** One owner of the markdown text, with splice as the only
mutation.

**Files:**
- Create: `src/textbuffer.h`
- Create: `src/textbuffer.cpp`
- Create: `tests/textbuffer_test.cpp`
- Modify: `CMakeLists.txt`

**Step 1: Write the header.**

```cpp
#pragma once
#include <string>
#include <cstdint>

// Owns the markdown source as UTF-8. All edits go through Splice.
class TextBuffer {
public:
    void SetText(std::string utf8);
    const std::string& Text() const { return text_; }
    size_t Length() const { return text_.size(); }

    // Replace [offset, offset+length) with replacement.
    // Returns the offset just past the inserted text.
    uint32_t Splice(uint32_t offset, uint32_t length,
                    const std::string& replacement);

    // Byte offset of the line containing offset, and of its end.
    uint32_t LineStart(uint32_t offset) const;
    uint32_t LineEnd(uint32_t offset) const;

    bool Dirty() const { return dirty_; }
    void ClearDirty() { dirty_ = false; }

private:
    std::string text_;
    bool dirty_ = false;
};
```

**Step 2: Write failing tests.**

```cpp
TEST(TextBuffer, SpliceInsertsAtOffset) {
    TextBuffer b;
    b.SetText("hello world");
    uint32_t end = b.Splice(5, 0, ",");
    EXPECT_EQ(b.Text(), "hello, world");
    EXPECT_EQ(end, 6u);
}

TEST(TextBuffer, SpliceReplacesRange) {
    TextBuffer b;
    b.SetText("hello world");
    b.Splice(0, 5, "goodbye");
    EXPECT_EQ(b.Text(), "goodbye world");
}

TEST(TextBuffer, LineStartFindsBOL) {
    TextBuffer b;
    b.SetText("one\ntwo\nthree");
    EXPECT_EQ(b.LineStart(5), 4u);
    EXPECT_EQ(b.LineEnd(5), 7u);
}
```

**Step 3: Implement.** A plain `std::string` with `replace` is correct and
fast enough to 1 MB. A piece table is the classic optimisation; it is YAGNI
here and can replace the internals later without changing the interface.

**Step 4: Add to CMake.** Append `src/textbuffer.cpp` to the source list and
`tests/textbuffer_test.cpp` to the test target.

**Step 5: Commit.**

```bash

git commit -m "feat: TextBuffer with splice-based editing"
```

### Task 3: Define caret and selection types

**Objective:** A vocabulary for "where the cursor is" that survives reparse.

**Files:**
- Create: `src/caret.h`
- Create: `tests/caret_test.cpp`

**Step 1: Write the header.**

```cpp
#pragma once
#include <cstdint>

// A caret position is a byte offset into the TextBuffer.
// Storing source offsets rather than block indices means the caret
// survives a reparse that renumbers blocks.
struct CaretPos {
    uint32_t offset = 0;
    bool operator==(const CaretPos& o) const { return offset == o.offset; }
    bool operator<(const CaretPos& o) const { return offset < o.offset; }
};

// A selection is an anchor and an active end. Anchor is where the
// drag started; active is where the mouse or shift-arrow is now.
struct Selection {
    CaretPos anchor;
    CaretPos active;

    bool Empty() const { return anchor == active; }
    uint32_t Start() const {
        return anchor < active ? anchor.offset : active.offset;
    }
    uint32_t End() const {
        return anchor < active ? active.offset : anchor.offset;
    }
    uint32_t Length() const { return End() - Start(); }
    void Collapse(CaretPos p) { anchor = p; active = p; }
};
```

**Step 2: Write tests** covering `Empty`, reversed selections where
`active < anchor`, and `Collapse`.

**Step 3: Commit.**

```bash

git commit -m "feat: CaretPos and Selection value types"
```

**Verification:** Tests pass. Nothing uses them yet.

### Task 4: Build the LayoutCache

**Objective:** Keep `IDWriteTextLayout` objects alive between frames so hit
testing works, and record where each block was drawn.

**Files:**
- Create: `src/layoutcache.h`
- Create: `src/layoutcache.cpp`
- Modify: `src/renderer.h`, `src/renderer.cpp`

**Step 1: Write the header.**

```cpp
#pragma once
#include <dwrite.h>
#include <vector>
#include <cstdint>
#include "dom.h"

// One entry per rendered block: the live layout plus the rect it
// occupied, in document coordinates (before scroll translation).
struct BlockLayout {
    IDWriteTextLayout* layout = nullptr;  // owned, may be null
    float x = 0.0f;
    float y = 0.0f;
    float width = 0.0f;
    float height = 0.0f;
    uint32_t srcOffset = 0;    // copied from Node
    uint32_t srcLength = 0;
    uint32_t textStartOffset = 0;  // source offset of layout char 0
    size_t nodeIndex = 0;
};

class LayoutCache {
public:
    ~LayoutCache();
    void Clear();
    void Add(BlockLayout bl);
    const std::vector<BlockLayout>& Blocks() const { return blocks_; }

    // Find the block whose rect contains (x, y). Returns -1 if none.
    int HitTestBlock(float x, float y) const;

    // Find the block owning a source offset. Returns -1 if none.
    int BlockForOffset(uint32_t offset) const;

private:
    std::vector<BlockLayout> blocks_;
};
```

**Step 2: Implement.** `Clear` releases every layout. `Add` takes ownership.
`HitTestBlock` walks the vector; a document with thousands of blocks would
want a binary search on `y`, which is a later optimisation.

**Step 3: Wire into the renderer.** In `Render`, instead of releasing each
layout at the end of the loop iteration, hand it to the cache. Add a
`LayoutCache* cache_` member and a `SetLayoutCache` setter so the app owns
the cache lifetime.

**Step 4: Commit.**

```bash
git add src/layoutcache.h src/layoutcache.cpp src/renderer.h src/renderer.cpp CMakeLists.txt
git commit -m "feat: LayoutCache retains text layouts for hit testing"
```

**Verification:** CI green, deploy, confirm rendering is unchanged and
memory does not grow across repeated scrolling. Watch Task Manager over a

### Task 5: Map between source offsets and screen points

**Objective:** The two functions every editor needs.

**Files:**
- Modify: `src/layoutcache.h`, `src/layoutcache.cpp`
- Create: `tests/hittest_test.cpp`

**Step 1: Add the two mapping calls.**

```cpp
    // Screen point to source offset. Used for mouse clicks.
    uint32_t PointToOffset(float x, float y) const;

    // Source offset to a caret rectangle. Used to place the caret.
    bool OffsetToCaretRect(uint32_t offset, float* outX, float* outY,
                           float* outH) const;
```

**Step 2: Implement `PointToOffset`.** Find the block with `HitTestBlock`,
then call `IDWriteTextLayout::HitTestPoint` with coordinates relative to the
block origin. That returns a UTF-16 text position within the layout. Convert
it to a source offset by adding `textStartOffset` and adjusting for the
UTF-16 to UTF-8 difference.

**Step 3: Implement `OffsetToCaretRect`.** Find the block with
`BlockForOffset`, convert the source offset to a UTF-16 position within the
layout, then call `HitTestTextPosition`.

**Step 4: Note the encoding trap.** The buffer is UTF-8, layouts are UTF-16.
Conversion is not a byte count. Write a helper pair:

```cpp
uint32_t Utf8OffsetToUtf16(const std::string& s, uint32_t byteOffset);
uint32_t Utf16OffsetToUtf8(const std::string& s, uint32_t u16Offset);
```

Test them explicitly with ASCII, with Danish characters, and with an emoji.

**Step 5: Commit.**

```bash
git add src/layoutcache.h src/layoutcache.cpp tests/hittest_test.cpp
git commit -m "feat: bidirectional offset and point mapping"
```

### Task 7: Click and drag to select

**Objective:** Mouse selection, rendered as a highlight.

**Files:**
- Modify: `src/app.cpp`, `src/renderer.cpp`

**Step 1: Handle the mouse triad.**

- `WM_LBUTTONDOWN`: `sel_.Collapse(PointToOffset(...))`, `SetCapture`.
- `WM_MOUSEMOVE` with `MK_LBUTTON`: `sel_.active = PointToOffset(...)`,
  repaint.
- `WM_LBUTTONUP`: `ReleaseCapture`.

**Step 2: Draw the selection.** In `Render`, before drawing each block's
text, if the selection overlaps that block's source range, call
`HitTestTextRange` for the overlapping portion and fill those rects with a
selection brush.

**Step 3: Add the color token.** In `theme.h`, add to `Palette`:

```cpp
    D2D1_COLOR_F selectionBg;   // 0xB4D5FE, the Windows selection blue
    D2D1_COLOR_F selectionText; // 0x000000
```

**Step 4: Handle double-click and triple-click.** Both are required
behaviour, not optional polish, because every text control on Windows has
them and users reach for them without thinking.

| Gesture | Selects |
|---------|---------|
| Double-click | the word under the cursor |
| Triple-click | the whole paragraph or block under the cursor |

`WM_LBUTTONDBLCLK` gives the double-click. Windows sends no triple-click
message, so track it manually: count a third `WM_LBUTTONDOWN` that arrives
within `GetDoubleClickTime()` of the double-click and within the
`SM_CXDOUBLECLK` by `SM_CYDOUBLECLK` rectangle of the previous point.

Word boundaries come from `IDWriteTextAnalyzer` or, more simply, from
scanning for whitespace in the buffer. Punctuation counts as its own word,
matching Notepad and Word. Paragraph boundaries come straight from the
`Node` the click landed in, using its `srcOffset` and `srcLength`, so a
triple-click inside a list item selects that item and a triple-click in a
table cell selects that cell.

Dragging after a double-click should extend by whole words, and after a
triple-click by whole blocks. This is the detail most implementations skip.

**Step 5: Shift plus click extends the selection.** When `WM_LBUTTONDOWN`
arrives with `MK_SHIFT`, keep `sel_.anchor` and move only `sel_.active`.
Without shift, collapse as in Step 1. This is the standard behaviour in
every text control and users notice when it is missing.

**Step 6: Select across blocks.** The selection is a source offset range, so
it already spans blocks. What needs work is the drawing: every block whose
source range intersects the selection draws its own highlight, and blocks
fully inside the range highlight from first to last character. Test a drag
that starts in a heading and ends three paragraphs down.

**Step 7: Autoscroll while dragging.** When `WM_MOUSEMOVE` reports a point
above or below the client rect with the button held, start a timer that
scrolls toward the mouse and keeps extending `sel_.active` until the button
is released or the mouse comes back inside. Scroll speed should grow with
the distance outside the rect, capped so it stays controllable.

**Step 8: Commit, deploy.**

**Verification:** Drag across a paragraph. A blue highlight follows the
mouse. Double-click selects exactly one word, with no trailing space.
Triple-click selects the whole paragraph, and inside a list it selects only
the item clicked. Double-click and then drag extends word by word. Click,
then shift plus click further
down; the range between the two points is highlighted. Drag below the window
edge and the view scrolls while the selection keeps growing. Selection
survives scrolling.

```cpp
// Applies edits to a TextBuffer and keeps a Selection consistent.
// Knows nothing about Win32 or Direct2D.
class EditController {
public:
    EditController(TextBuffer* buf, Selection* sel)
        : buf_(buf), sel_(sel) {}

    void InsertText(const std::string& utf8);
    void DeleteBackward();
    void DeleteForward();
    void DeleteSelection();

private:
    TextBuffer* buf_;
    Selection*  sel_;
};
```

**Step 2: Implement `InsertText`.**

```cpp
void EditController::InsertText(const std::string& utf8) {
    if (!sel_->Empty()) DeleteSelection();
    uint32_t at = sel_->active.offset;
    uint32_t end = buf_->Splice(at, 0, utf8);
    sel_->Collapse({end});
}
```

**Step 3: Handle `WM_CHAR` in the content window.** Filter out control
characters below 0x20 except tab, convert the UTF-16 code unit to UTF-8,
and call `InsertText`. Surrogate pairs arrive as two `WM_CHAR` messages;
buffer the high surrogate and wait for the low one.

**Step 4: Reparse and repaint.** After every edit, call a new
`AppWindow::OnBufferChanged()` that reparses, clears the layout cache,
recomputes scroll extent, and repaints. Task 12 makes this incremental.

**Step 5: Commit, deploy.**

**Verification:** Click in a paragraph and type. Characters appear as
rendered text, not as markdown source. Type `**` and nothing bolds yet,
which is expected until Task 14.

### Task 9: Backspace, delete, and Enter

**Objective:** The three structural keys.

**Files:**
- Modify: `src/editcontroller.cpp`, `src/app.cpp`

**Step 1: Implement backward and forward delete.** Both must step by
grapheme cluster, not by byte, or backspacing an emoji leaves half a
surrogate pair. Use ICU's `ubrk_open(UBRK_CHARACTER, ...)` when available.

```cpp
void EditController::DeleteBackward() {
    if (!sel_->Empty()) { DeleteSelection(); return; }
    uint32_t at = sel_->active.offset;
    if (at == 0) return;
    uint32_t prev = PrevGraphemeBoundary(buf_->Text(), at);
    buf_->Splice(prev, at - prev, "");
    sel_->Collapse({prev});
}
```

**Step 2: Handle Enter contextually.** This is where WYSIWYG earns its
keep. Pressing Enter should do what the user means:

| Context | Behaviour |
|---------|-----------|
| In a paragraph | insert `\n\n`, starting a new paragraph |
| At the end of a list item | insert `\n- ` or `\n1. `, continuing the list |
| On an empty list item | remove the marker, ending the list |
| Inside a code block | insert a single `\n` |
| At the end of a heading | insert `\n\n`, dropping to body style |

Implement it as `EditController::InsertParagraphBreak(const Node& ctx)`,
with the context node found from the caret offset.

**Step 3: Handle `WM_KEYDOWN` for `VK_BACK`, `VK_DELETE`, `VK_RETURN`.**

**Step 4: Write unit tests** for `InsertParagraphBreak` across all five
contexts, driving `EditController` directly with no UI.

**Step 5: Commit, deploy.**

**Verification:** Backspace deletes one visible character, including for
Danish `å` and for an emoji. Enter at the end of a list item creates the
next bullet automatically.

### Task 10: Arrow keys, Home, End, and Shift selection

**Objective:** Full keyboard navigation.

**Files:**
- Modify: `src/app.cpp`
- Create: `src/navigation.h`, `src/navigation.cpp`

**Step 1: Left and right** step by grapheme boundary. With Ctrl held, step
by word. With Shift held, move `sel_.active` and leave `sel_.anchor` alone.

**Step 2: Up and down are visual, not logical.** They must move by rendered
line, which means going through the layout, not the buffer:

```cpp
// Take the caret's screen point, move one line height up or down,
// then hit test back to an offset.
uint32_t MoveVertical(const LayoutCache& lc, uint32_t offset,
                      int direction, float* desiredX);
```

**Step 3: Preserve the desired column.** A user pressing Down repeatedly
through lines of varying length expects the caret to return to its original
column. Store `desiredX_` in `AppWindow` and reset it to -1 on any
horizontal movement or edit.

**Step 4: Home and End** map to the start and end of the visual line, again
via the layout. Ctrl+Home and Ctrl+End go to document start and end.

**Step 5: Page Up and Page Down** move by the client height in DIPs.

**Step 6: Ctrl+A selects the whole document.** Set `sel_.anchor` to offset 0
and `sel_.active` to `buffer_.Length()`. Handle it in `WM_KEYDOWN`, not
`WM_CHAR`, and make sure it also works in read-only mode from Task 20.

**Step 7: Shift applies to every motion, not just the arrows.** Route all
navigation through one helper so the rule lives in a single place:

```cpp
// Move the caret and either collapse the selection or extend it.
void MoveCaret(Selection* sel, uint32_t newOffset, bool extend);
```

Shift+Home, Shift+End, Shift+Ctrl+Home, Shift+Ctrl+End, Shift+Page Up and
Shift+Page Down all fall out of this for free. Without the shared helper
these get implemented one at a time and half of them get forgotten.

**Step 8: Commit, deploy.**

**Verification:** Hold Down through a document with mixed line lengths. The
caret keeps its column. Shift+Down extends a selection one line at a time.
Ctrl+A highlights the whole document. Shift+Ctrl+End from the middle selects
everything to the end.

### Task 11: Undo and redo

**Objective:** Ctrl+Z and Ctrl+Y, with sensible grouping.

**Files:**
- Create: `src/undostack.h`, `src/undostack.cpp`
- Create: `tests/undo_test.cpp`
- Modify: `src/editcontroller.cpp`

**Step 1: Record splices, not snapshots.** A snapshot per keystroke wastes
memory on large documents. Each undo entry is the inverse splice:

```cpp
struct UndoEntry {
    uint32_t offset;
    std::string removed;    // what was there before
    std::string inserted;   // what replaced it
    Selection selBefore;
    Selection selAfter;
    uint64_t timestamp;     // for coalescing
};
```

**Step 2: Coalesce runs of typing.** Merge a new entry into the previous one
when all three hold: same edit type, contiguous offsets, and under 800 ms
apart. Without this, Ctrl+Z undoes one letter at a time and users hate it.

**Step 3: Break coalescing** on caret movement, on any delete after an
insert, and at a whitespace character. Typing a word then a space should
undo as one unit.

**Step 4: Route every mutation through the stack.** `EditController` gains
an `UndoStack*` and pushes before applying.

**Step 5: Write tests** covering coalescing, a break on caret move, redo
after undo, and redo being cleared by a fresh edit.

**Step 6: Commit, deploy.**

**Verification:** Type a sentence, press Ctrl+Z once. The whole sentence
disappears, not the last letter. Ctrl+Y restores it.

### Task 12: Incremental reparse

**Objective:** Keep typing responsive on large documents.

**Files:**
- Modify: `src/parser.h`, `src/parser.cpp`
- Modify: `src/app.cpp`
- Create: `tests/incremental_test.cpp`

**Step 1: Measure first.** Before optimising, instrument the full reparse

### Task 13: Copy, cut, and paste

**Objective:** Clipboard integration that does the right thing on paste.

**Files:**
- Create: `src/clipboard.h`, `src/clipboard.cpp`
- Modify: `src/app.cpp`

**Step 1: Copy puts two formats on the clipboard.** `CF_UNICODETEXT` gets

**Step 4: Cut is copy then `DeleteSelection`.**

**Step 5: Commit, deploy.**

byte-identical to the source.

### Task 16: Suppress markdown syntax during typing

**Objective:** Typing markdown characters must not silently create

**Files:**

```cpp
// Return the bytes to splice for a typed character at this offset,
```

### Task 16b: Table editing from the ribbon

**Objective:** Insert and edit tables as a grid. The user clicks in a cell,
types, presses Tab to move on, and adds rows and columns from the ribbon.
The pipes and dashes stay invisible.

**Files:**
- Create: `src/tableedit.h`, `src/tableedit.cpp`
- Create: `tests/tableedit_test.cpp`
- Modify: `src/formatting.cpp`, `src/layoutcache.cpp`
- Modify: `src/ribbon.xml`, `src/ribbon.cpp`, `src/app.cpp`

**Why this is its own task.** Every other block is one run of text. A table
is a grid where a single edit in one cell can change the width of a whole
column, and where the markdown source keeps a separator row that has no
visual counterpart. The renderer already draws tables, so this task is about
the model and the input, not the pixels.

**Step 1: Give the DOM a table model.** The parser currently flattens table
content. Add to `dom.h`:

```cpp
struct TableCell {
    uint32_t srcOffset = 0;     // start of the cell text in the source
    uint32_t srcLength = 0;
    std::vector<InlineBlock> inlines;
};

struct TableRow {
    std::vector<TableCell> cells;
    bool isHeader = false;
};

enum class ColumnAlign { Default, Left, Center, Right };
```

`Node` for a table gains `std::vector<TableRow> rows` and
`std::vector<ColumnAlign> aligns`. md4c reports the alignment in
`MD_BLOCK_TH_DETAIL` and `MD_BLOCK_TD_DETAIL`, so nothing needs parsing by
hand.

**Step 2: Extend the LayoutCache to cells.** Each cell gets its own
`BlockLayout` entry with its own rect, plus a `(nodeIndex, row, col)` key.
Hit testing then lands in a cell rather than on the table as a whole, and
the caret works inside a cell exactly as it does in a paragraph.

**Step 3: Add a Table group to the ribbon.**

| Ribbon control | Command id | Effect |
|----------------|-----------|--------|
| Insert table | `cmdInsertTable` | size picker gallery, rows by columns |
| Insert row above | `cmdRowAbove` | new empty row |
| Insert row below | `cmdRowBelow` | new empty row |
| Insert column left | `cmdColLeft` | new empty column |
| Insert column right | `cmdColRight` | new empty column |
| Delete row | `cmdDeleteRow` | remove the row at the caret |
| Delete column | `cmdDeleteCol` | remove the column at the caret |
| Align left, center, right | `cmdColAlign*` | set the column alignment |

The whole group is disabled unless the caret sits inside a table, using the
`UI_PKEY_Enabled` property. Insert table stays enabled everywhere.

**Step 4: Implement the structural operations.**

```cpp
void InsertTable(TextBuffer* buf, Selection* sel, int rows, int cols);
void InsertRow(TextBuffer* buf, const Document& doc,
               size_t node, int atRow);
void DeleteRow(TextBuffer* buf, const Document& doc,
               size_t node, int atRow);
void InsertColumn(TextBuffer* buf, const Document& doc,
                  size_t node, int atCol);
void DeleteColumn(TextBuffer* buf, const Document& doc,
                  size_t node, int atCol);
void SetColumnAlign(TextBuffer* buf, const Document& doc,
                    size_t node, int col, ColumnAlign a);
```

Every one of them rewrites the whole table block in the buffer as a single
splice, which keeps it one undo step. This is the one place the plan does
reserialise a block the user did not fully touch, so preserve the original
padding style: if the source table was aligned with spaces, keep it aligned;
if it was compact, keep it compact.

**Step 5: Wire the keyboard inside a table.**

| Key | Effect |
|-----|--------|
| Tab | next cell, wrapping to the next row |
| Tab in the last cell | append a new row and move into it |
| Shift+Tab | previous cell |
| Up and Down arrow | same column, adjacent row |
| Enter | new line inside the cell, not a new row |

Tab must not fall through to the list indent handler from Task 15 when the
caret is inside a table.

**Step 6: Escape pipes typed by the user.** A literal `|` typed into a cell
becomes `\|` in the source, otherwise it splits the cell. This extends the
Task 16 input filter with a table-aware case.

**Step 7: Handle the degenerate cases in tests.** Deleting the last column
deletes the table. A one-row table still needs its separator row. A cell
containing bold or a link must survive a column insert unchanged.

**Step 8: Commit, deploy.**

**Verification:** Click Insert table and pick three by three. An empty table
appears with a header row. Type in a cell, press Tab, type in the next one.
Press Tab in the last cell and a fourth row appears. Click Insert column
right; the column lands and the existing text is untouched. Set a column to
right aligned and the numbers move right. At no point are pipe characters
visible on screen.

## Follow-up notes and known gaps

This section records what the plan deliberately leaves out, plus one defect
found in the current build. Keep it updated as tasks land, so the gap list
is honest rather than aspirational.

### Known defect: selection is not visible

**Symptom:** Text can be selected, but no highlight is drawn. The selection
range is tracked correctly, since copy returns the right text, but nothing
appears on screen.

**Likely cause:** `Render` releases each `IDWriteTextLayout` per frame and
draws text without first filling the selection rects. Steps 2 and 6 of Task
7 cover the fix, and they depend on the LayoutCache from Task 4 keeping the
layouts alive long enough to call `HitTestTextRange`.

**What to check when fixing it:**

1. Is `selectionBg` actually present in `Palette` and initialised for both
   the light and the dark theme, or only one of them.
2. Is the highlight drawn before the text, since drawing it after paints
   over the glyphs.
3. Does the highlight use document coordinates or client coordinates. A
   missing scroll translation puts the rects offscreen, which looks exactly
   like nothing being drawn.
4. Does a block fully inside the selection highlight end to end, not just
   the first and last block of the range.

**Verification:** Drag across three paragraphs. All three are highlighted,
including the whole of the middle one, in both themes and after scrolling.

## Risks, tradeoffs, and open questions

**The round-trip problem is the deepest risk.** Markdown has many ways to
express the same thing: `*` and `_` for emphasis, setext and ATX headings,
two spaces versus a backslash for a hard break. An edit that reserialises a
block must preserve the user's original style. Mitigation: never reserialise
a block the user did not touch, and splice text rather than regenerate.

**Source offsets are fragile.** Every edit shifts the offsets of everything
after it. A single missed adjustment puts the caret in the wrong place, and
the bug will be intermittent and hard to reproduce. Mitigation: one
`ShiftOffsets(from, delta)` function that all edits route through, plus an
assertion in debug builds that offsets are monotonic across the node list.

**TSF is a large surface for a small team.** `ITextStoreACP` has around 20
methods. Consider deferring Task 19 and shipping with basic `WM_IME_CHAR`
support, which covers Western input and simple IME cases, then upgrading.
The tradeoff is that CJK users get a degraded experience in the interim.

**UI Automation may be a compliance requirement, not a nice-to-have.** For
AU deployment, check whether WCAG or the Danish accessibility rules apply
before scheduling Task 21 late. If they do, it moves ahead of Task 19.

**Tables are the hardest editing surface.** Task 16b covers them, but it is
the task most likely to overrun. The risk is the reserialise step: rewriting
a whole table block on every structural change is the one place the plan
regenerates markdown the user wrote by hand. Mitigation: snapshot the
padding style on parse and reproduce it. If the task slips, it can ship
after M4 without blocking anything else, since tables still render and cell
text is still editable without it.

**Scope check: what is deliberately excluded.**

- Syntax highlighting inside code blocks. Needs a lexer per language.
- Spell checking. Windows offers `ISpellChecker`, but it is a project.
- Find and replace. Straightforward, but not WYSIWYG-specific.
- Multiple documents or tabs. Architectural, affects everything.
- Collaborative editing. A different application entirely.

**Open question: does the ribbon survive?** A ribbon suits a document editor
well, but the Fil button fight in this project's history suggests friction.
Worth deciding before Task 14 adds a Format group.

### Task 22 status: measured, and one budget is 100x over

The harness existed but measured the wrong things under the right names, so
it passed without testing the plan's budgets. Rewritten to measure the five
budgets on a real 1 MB fixture, taking the median of five runs.

The fixture was 670 KB of 5000 identical paragraphs, which never exercised
heading, list, code or quote layout. It is now 1.05 MB with a mix of
paragraphs, headings, bullet and ordered lists, fenced code and blockquotes.

Numbers on this host, 15280 blocks:

| Budget | Measured | Budget | State |
|--------|----------|--------|-------|
| Open a 1 MB document | 470 ms | 500 ms | met, 94% used |
| Splice insert+delete | 0.03 ms | 16 ms | met, 0.2% used |
| Reparse one character | **463 ms** | **5 ms** | **missed, 92x over** |

### Why the reparse budget fails

`ParseMarkdownIncremental` is not implemented. It ignores `oldDoc`,
`editOffset`, `oldLen` and `newLen`, and calls `ParseMarkdown`. Plan Task 12
steps 2 and 3, finding the dirty block range and reparsing only that slice,
were never written. The correctness test in `tests/incremental_test.cpp`
passes precisely because a full reparse is trivially identical to itself.

`AppWindow::ScheduleReparse` debounces with a 150 ms timer, which fires
sooner than the 463 ms of work it defers, so the debounce hides nothing.

**What this costs a user:** typing in a 1 MB document reparses half a
megabyte of markdown per keystroke and stalls visibly. Below 100 KB
`ScheduleReparse` reparses inline with no timer, so ordinary documents are
unaffected.

The budget is recorded as a known gap rather than deleted. See the
`TEST_XFAIL` note in `tests/perf_harness.cpp`. Deleting the assertion would
make CI green while the editor still stalls.

Two budgets remain unmeasured: full relayout on resize, and scroll one page.
Both need a DirectWrite factory and a render target, which the test harness
does not create. `Renderer::Measure()` is the relayout path and takes no
render target, so it is measurable with a factory; scroll needs
virtualisation, which `Render()` does not yet do.

### Task 16b status: what has landed

Table editing is implemented in `src/app.cpp` (commands), `src/navigation.cpp`
(offsets and rewrites), `src/dom.h` and `src/parser.cpp` (model), and
`src/renderer.cpp` (drawing). Measured against the steps above:

| Step | State |
|------|-------|
| 1. Table model with `ColumnAlign` | Done. `ColumnAlign` and `Node::aligns` added, populated from md4c's `MD_BLOCK_TD_DETAIL.align`. |
| 2. Per-cell layout entries | Done differently. Cells are separate `BlockLayout` entries hit-tested by band, and carry a `u16ToSrc` map rather than a `(row, col)` key. The key was unnecessary once cell hit testing worked. |
| 3. Ribbon group and enable state | Done. Enabled state comes from `CaretTableCapabilities()`, so a button is never live when the command would refuse. |
| 4. Structural operations as one splice | Done. `TableInsertColumn`, `TableRemoveColumn`, `TableSetColumnAlign` each return the rewritten table span and the caller splices once, so one operation is one undo step. |
| 5. Keyboard inside a table | Done. `Tab`, `Shift+Tab` and Up/Down walk cells and rows; Up/Down keep the column via `TableVerticalMove`. `Enter` remains a documented no-op, because markdown tables have no line break inside a cell. |
| 6. Escape a typed pipe | Done, and scoped. A `|` is escaped only inside a table cell, where it would split the cell. Outside a table it is left alone. |
| 7. Degenerate cases | Covered by `tests/table_interaction_test.cpp`. |

Two things in step 4 need recording, because they are the sharp edges:

* **Deleting the last column does not delete the table.** The command refuses
  and the ribbon button is disabled. The plan said the table should go; the
  refusal is the safer reading, since a mis-click should not destroy content.
* **Padding style is preserved.** `TableSetColumnAlign` trims the cell to its
  dash run and keeps the dash count, so `| ---: |` stays spaced and `|---|`
  stays compact.

`TableAlignMark::None` clears a marker. A cell shorter than three dashes is
padded to three, because `:-` is not a cell md4c reads back as a delimiter.

**Still open in 16b:** rectangular selection by cell region, which the plan
lists as out of scope, and column-width dragging, which the plan does not
mention and the table guidelines do (§31).

**Open question: how much of the 22 tasks is actually wanted?** Tasks 1
through 10 produce a working plain-text editor with rendered output. Tasks
11 through 16 make it a real editor. Tasks 17 through 22 make it shippable.
There are natural stopping points at 10 and at 16.
