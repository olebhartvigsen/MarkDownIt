# Keeping the Windows and macOS ports aligned

*2026-11-09. Plan only. Nothing in this file has been implemented.*

## Why this exists

The architecture is a shared core with a native shell per platform. That
shape is right and matches what Scintilla, Slack's LibSlack and Zed do.
The weak point is where the shared core ends. It ends below the renderer
and below the app controller, so most behavior is written twice.

Measured on 2026-11-09 from `CMakeLists.txt` and the sources:

| Group | Files | Lines |
|-------|-------|-------|
| Shared by both builds | 42 | about 21,300 |
| Windows only | 16 | about 15,500 |
| macOS only | 26 | about 16,700 |

The two renderers are `src/renderer.cpp` (3,009 lines) and
`src/macos/renderer_mac.cpp` (2,720 lines). The two app controllers are
`src/app.cpp` (7,008 lines) and `src/macos/app_mac.cpp` (1,816 lines).
Only the margin arithmetic in `src/blockspacing.h` is shared between the
renderers.

## Findings

1. **Renderer written twice.** Table, list, code block and quote layout
   exist in both renderers.
2. **App controller written twice.** Bold, insert table, undo, open and
   the heading commands are implemented on each side
   (`AppWindow::ToggleBold` against `App::ToggleInlineWithPending`).
3. **The seam is one-sided.** `src/macos/seams.h` says the Windows
   renderer keeps calling Direct2D and that moving it onto the seams is
   optional. Nothing forces a new feature onto both sides.
4. **Features already differ.** `src/mermaid/state_parse.cpp` and
   `state_layout.cpp` are compiled on macOS only. The mac build globs
   `src/mermaid/*.cpp`. The Windows exe lists its files by hand. That is
   the likely cause, not confirmed.
5. **`#ifdef _WIN32` inside shared files.** `src/settings.cpp` is about
   190 of 239 lines of Registry code. `clipboard.cpp`, `parser.cpp` and
   `markers.cpp` carry smaller branches.
6. **Four hand-kept source lists.** The Windows exe, the mac core library,
   the mac app and the two test targets each list files themselves.
   `tools/check_mac_sources.py` only covers `src/macos/`.
7. **Duplicated constants.** `renderer.cpp` has 192 float literals,
   `renderer_mac.cpp` has 139. The bullet glyphs live only in the mac
   renderer. `LayoutMetrics` in `src/theme.h` covers part of it.
8. **Coarse parity checks.** `tools/compare_platform_captures.py` allows
   3 to 5 px per row. There is no Windows renderer test, only
   `tests/renderer_mac_test.cpp`, and no list of which feature exists where.

## Research that shaped the plan

- Scintilla keeps a small portability layer (`Surface`, `Font`) that every
  platform implements, so the core never touches a platform API
  (scintilla.org/Design.html).
- Slack found that building features once per platform produced the same
  bug several times and different behavior on each client. It moved logic
  into one core library and kept UI and OS access native
  (slack.engineering, LibSlack).
- Chromium has an open issue to replace per-platform `RenderText` classes
  with one HarfBuzz plus Skia path, because per-platform text code drifts
  (issues.chromium.org/issues/40078432).
- Zed says abstraction works only if the platform stays behind one API,
  with a direct escape hatch where native depth matters
  (zed.dev/blog/zed-decoded-linux-when).
- Codename One ties each port's support claim to a conformance test that
  must pass, not to a statement.

Not read in full: the Chromium cross-platform UI document and the
Codename One article. Only their search snippets informed this plan.

## Goal

A feature added to the document model, layout or editing behavior reaches
both platforms by construction. Where a platform differs on purpose, the
difference is written down and checked by CI.

## Rules for all batches

- No commit or push without the user's permission.
- No branch unless the user asks for one.
- The Windows build stays green after every batch. The compile gate is CI
  (`windows-2022` and `macos-26`).
- Text for docs and commits goes through the humanizer skill, no em dashes.
- Editing behavior stays inside the four specs named in `AGENTS.md`.
  Goldens never change to match new output.

## Automated alignment in the build pipeline

The goal is that drift fails a build, so nobody has to notice it by
eye. Each gate below names the finding it catches.

### What the pipeline does today

Read from `.github/workflows/build.yml` on 2026-11-09:

- `build` (`windows-2022`) builds, runs `MarkDownIt.tests.exe` and dumps
  the SVG drawing commands.
- `test-macos` runs the same test suite on `macos-26` and dumps the same
  SVG commands.
- `build-macos` runs the mac-only checks: `check_mac_menu.py`,
  `check_shared_guards.py`, `check_mac_sources.py`, `check_mac_chrome.py`,
  `check_mac_bundle.py` and the launch smoke.
- `svg-parity` (`ubuntu-latest`, needs both platform jobs) downloads both
  JSON dumps and compares them. This is the pattern to copy: each
  platform produces data, one cheap job compares it.
- `oracle` and `verify-export` check Mermaid geometry and Word and PDF
  output against independent readers.
- The Windows capture step and the `capture-parity` job are switched
  off with `if: ${{ false }}` (commit `73907cf`, 2026-11-06, no message
  body) under a reading of the policy that the user has since
  corrected: screenshots are allowed in the pipeline, not locally. The macOS launch smoke still captures
  and uploads `MarkDownIt-window-capture` on every run, so one half of
  the pair exists and the other half is dark. This plan turns both back
  on (task 1.7).
- `check_shared_guards.py` runs only in the macOS build job. A Windows
  header slipped into a shared file would be found late.

### New gates

Every gate is a script in `tools/`, has a unit test with a deliberately
broken input (the way `tools/test_check_svg_parity.py` tests the SVG
checker), and prints a short reason on failure.

| Gate | Runs where | Catches | Added in |
|------|------------|---------|----------|
| Static alignment job | `ubuntu-latest`, no build, under one minute | findings 4, 5, 6, 8 | Batch 1 |
| Test inventory parity | both test jobs plus one `ubuntu-latest` compare job | a test compiled on one platform only | Batch 1 |
| Layout dump parity | both test jobs plus the compare job | findings 1 and 7 | Batch 2.3 and 3 |
| Editing transcripts | both test jobs | finding 2 | Batch 4 |
| Seam conformance | both test jobs and the portable build | finding 3 | Batch 2.2 |
| Paired-file advisory | `ubuntu-latest`, on every push | one renderer or controller changed alone | Batch 1 |
| Capture parity (on) | `windows-2022` and `macos-26` capture, `ubuntu-latest` compares | font, paint and chrome differences, a dead window | Batch 1.7 |

#### Static alignment job

A new job `alignment-static` in `build.yml`, no checkout of build tools,
Python only. It runs:

1. `tools/check_sources_listed.py` (Batch 1.1): every source file is in
   exactly the manifest lists it belongs to.
2. `tools/check_parity_ledger.py` (Batch 1.2): every feature that exists
   on one platform has a ledger row with a reason.
3. `tools/check_command_coverage.py` (Batch 1.3): every ribbon command has
   a mac menu or toolbar entry, or a ledger row.
4. `tools/check_shared_guards.py` and `tools/check_mac_sources.py`, moved
   here from `build-macos` so they fail in seconds and on every push.
5. The unit tests of those checkers.

The other jobs list it under `needs`, so a drifted manifest stops the run
before the expensive builds start.

#### Test inventory parity

Same tests, same names, on both runners.

- Add a `--list` flag to `tests/gtest_lite.h` that prints one
  `suite.case` per line without running anything. Check first whether the
  framework already has one.
- Each test job writes `test-inventory-<platform>.txt` and uploads it.
- A new job `test-inventory-parity` downloads both and fails when a test
  exists on one side only, unless the ledger lists it as platform
  specific (for example the Win32 find bar window test, which
  `CMakeLists.txt` already says stays Windows only).
- This is the guard that would have caught the state diagram files being
  built on macOS only.

#### Layout dump parity

The deterministic core of the plan. It depends on the fake measurer in
Batch 2.3.

- Add `tests/layout_dump.cpp`. It lays out every file in
  `tests/fixtures/parity/*.md` with the fake text engine and writes a
  canonical JSON file: block order, rectangles, line breaks, table column
  widths, list marker positions and the display list from Batch 3.
- Build it into both test targets, the way `svg_parity_dump.cpp` is built
  into both today.
- Two checks:
  1. Each platform job diffs its own dump against a committed golden in
     `tests/layout-golden/`. A failure then names the platform that moved.
  2. The compare job diffs the Windows dump against the macOS dump. This
     is the backstop if a golden was updated wrongly.
- Goldens change only through `tools/update_layout_goldens.py`, never by
  hand, and the change shows in the diff for review. This follows the
  same rule `AGENTS.md` sets for the Office goldens.
- The fixture set must cover every block type in the layout order of
  Batch 3.2, plus nested lists, wide tables, long words, CJK text, emoji
  and right to left text. Add a fixture with each bug fix.

#### Editing transcripts

Turns the acceptance criteria in the editing specs into data both
platforms run.

- Create `tests/transcripts/*.json`. Each file holds a start text, a
  sequence of commands or key events, and the expected text, selection and
  undo depth after each step.
- A runner in `tests/transcript_test.cpp` feeds them through the shared
  document controller from Batch 4.
- Seed the corpus from the lists in
  `references/windows-standardtekstredigering-specifikation.md`,
  `references/word-processor-guidelines.md` (criteria A to H) and
  `references/word-processor-table-guidelines.md`.
- Before Batch 4 exists, run the transcripts through `EditController`
  directly, which both apps already share.
- The runner writes a result file per platform, and the compare job diffs
  them. Equality on the shared code is expected. A difference means a
  platform branch changed behavior.

#### Seam conformance

One suite, three engines (DirectWrite, Core Text, generic), the same
assertions. Defined in Batch 2.2. The suite runs in `build`,
`test-macos` and the portable build. Positions are UTF-16 code units in
all three, which the suite checks with surrogate pairs and combining
marks.

#### Paired-file advisory

A small script `tools/check_paired_changes.py` reads the pairs from the
ledger (`src/renderer.cpp` with `src/macos/renderer_mac.cpp`,
`src/app.cpp` with `src/macos/app_mac.cpp`, and so on). It looks at the
commits in the push range.

- If one side of a pair changed and the other did not, it prints a
  warning annotation.
- A `Parity:` line in the commit message (for example
  `Parity: macOS not affected, layout only on Windows`) silences it and
  records the reason.
- Start as a warning. Promote it to a failure after a month if the
  warnings turn out to be accurate.
- The pair list shrinks as Batches 3 and 4 move code into shared files,
  so the check retires itself.

#### Capture parity (switched on in Batch 1.7)

Both platforms photograph the same named states of the same document and
a compare job checks them. This is the only gate that sees the real
window, so it stays on permanently.

- **Windows capture.** Remove the `if: ${{ false }}` guard on the
  "Capture the states (QA walk)" step in the `build` job. It runs
  `tools/windows-smoke/capture.ps1` on the `windows-2022` runner against
  `tests/fixtures/layout-showcase.md`.
- **Compare job.** Remove the guard on `capture-parity`. It downloads
  `MarkDownIt-window-capture` (mac) and `MarkDownIt-windows-capture`
  and runs `tools/compare_platform_captures.py`.
- **Fix the artifact paths.** The job downloads the mac files to
  `captures/macos` and passes `captures/macos/qa`, and the Windows files
  go to `captures/windows`. The Windows upload step lists
  `build-win/qa/*.png`, so the files land under `qa/`. Check both
  layouts in the first run's "Show what was downloaded" step and correct
  the `--windows` argument if it needs `captures/windows/qa`.
- **Run it as a hard failure from the start**, not advisory. The
  comparison already has thresholds tuned against real captures (see
  `references/macos-qa.md`), and it fails on a dead window, a missing
  state or unreadable ink. An advisory gate was how this one went
  unnoticed.
- **Keep the uploads `if: always()`** so a red run still publishes the
  side by side and overlay pictures for the state that failed.
- **Hold the line on thresholds.** Do not loosen
  `tools/compare_platform_captures.py` to get green. Tighter checks on
  layout go in the layout dump, because fonts differ between Segoe UI and
  SF Pro.
- **Add the states the plan introduces.** The walk covers `doc`, `find`,
  `edit`, `outline`, `source`, `lower`, `end`, `tail`, `tail2`. Each
  batch that adds a visible feature adds its state to both walks and to
  the ledger.

### Pipeline shape after the plan

1. `alignment-static` (seconds). Everything else needs it.
2. `build`, `test-macos`, `build-macos` in parallel. Each runs the full
   test suite, the seam conformance suite, the layout dump, the
   transcripts and the test inventory.
3. Compare jobs on `ubuntu-latest`, needing both platform jobs:
   `svg-parity` (exists), `test-inventory-parity`, `layout-parity`,
   `transcript-parity`.
4. `capture-parity` (on again), needing `build` and `build-macos`,
   plus `oracle` and `verify-export` (exist).

The compare jobs follow the existing `svg-parity` job: download the two
artifacts, run a Python script, upload the diff when it fails.

### Making it bite

- **Push to main triggers CI after the fact.** The repository workflow in
  `AGENTS.md` pushes to main, so a required status check cannot block the
  push. Add `tools/check_alignment.sh` that runs the whole static job
  locally, and call it before every push. It is Python only and runs in
  WSL. It does not start any Windows program.
- **Check the triggers.** Confirm that no `paths` or `paths-ignore` filter
  in `build.yml` skips a platform job when a shared file changes. A shared
  change must run both platform jobs.
- **Failures must say what to do.** Every checker ends with the file to
  edit or the command to regenerate (`python3 tools/update_layout_goldens.py`).
- **Time budget.** The static job and the dumps add well under two
  minutes. The macOS queue, not the new gates, is the slow part.
- **No flaky gates.** The layout dump uses the fake measurer, so no font
  or OS version reaches it. Gates that read real fonts stay advisory.
- **Retire gates.** When Batch 3 finishes, the paired-file advisory for
  renderers goes away. When Batch 4 finishes, the same goes for the
  controllers.

| 5 | small | low | Batch 2.3, Batch 3 |

Batches 3 and 4 are independent and can run in either order. Start with
Batch 1 in full, then decide between 3 and 4 from what the ledger shows.

## Risks

- **Windows regression.** Moving the Windows renderer onto shared layout
  can change pixels. Mitigation: one block type per step, capture
  comparison and goldens before and after.
- **Font differences.** Segoe UI and SF Pro wrap differently, so shared
  layout with real fonts will not be byte identical. Goldens use the fake
  measurer for exactly this reason.
- **Performance.** The shared layer must keep the layout cache behavior
  (`src/layoutcache.cpp`). Check with the `markdownit-ui-perf` skill's
  scenarios (find, typing, scroll) before and after Batch 3.
- **Scope creep.** The seams stay narrow. A new platform call goes in only
  when a renderer needs it and both engines can answer it.
- **Capture flakiness.** A screen grab on a hosted runner can return a
  black frame or miss a state. The compare job already fails on a dead
  window, so a bad grab shows as red, not as a silent pass. If it flakes,
  fix the capture (wait for the state announcement in `walk.log`), do not
  retry blindly.
- **Gate noise.** A gate that fails for reasons nobody can act on gets
  ignored. Each gate ships with a unit test and a plain failure message,
  and the advisory ones stay warnings until they have been right for a
  month.
- **Golden churn.** Layout goldens that change on every feature teach
  people to regenerate without looking. Regeneration goes through one
  script and the diff is reviewed.
- **No Linux target.** The portable `textlayout_generic.cpp` exists for
  tests only. This plan does not add a third platform.

## Open questions

1. Should the Windows build get state diagrams, or stay without them on
   purpose? The ledger needs a decision either way.
2. Is the Windows content width cap (`maxContentWidth`) permanent? It is
   the one deliberate layout difference named in `theme.h`.
3. Is Batch 3 worth its cost, or is Batch 1 plus the ledger enough for the
   size of this project? The answer depends on how often the two renderers
   have diverged in the last months. `git log` on the two renderer files
   would give a rough count.

## Done when

- A single manifest feeds every target, and CI fails on an unlisted file.
- `references/platform-parity.md` exists, CI checks it, and every
  difference has a reason.
- Both renderers paint one shared display list for every block type.
- Both apps call one document controller for every editing command.
- The cross-platform golden diff is byte identical on both runners.
- The screenshot comparison runs on every push, publishes its pictures,
  and is a required check.
- Every gate in the pipeline section runs on every push, each has a unit
  test with a broken input, and a drift of the kind in findings 1 to 8
  turns a job red.
