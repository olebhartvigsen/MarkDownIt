# Keeping the Windows and macOS ports aligned

*2026-11-09, corrected 2026-11-27. Most of this plan has landed. The batches
below are kept as the record of what was decided and why; the status section
directly under this line says what is true now and what is actually left.*

## Why this exists

The architecture is a shared core with a native shell per platform. That
shape is right and matches what Scintilla, Slack's LibSlack and Zed do.
The weak point was where the shared core ended. It ended below the renderer
and below the app controller, so most behavior was written twice. Batches 1 to
4 moved that line: layout, the display list and the editing commands are
shared now, and what is still per platform is the painting itself (see the
status section).

Measured on 2026-11-09 from `CMakeLists.txt` and the sources, and again on
2026-11-26 from `cmake/sources.cmake` and the tree:

| Group | 2026-11-09 (approximate) | 2026-11-26 (from the manifest and the tree) |
|-------|-----------|-----------|
| Shared by both builds | 42 files, about 21,300 lines | 69 files, 30,195 lines |
| Windows shell only | 16 files, about 15,500 lines | 24 files, 19,293 lines |
| macOS shell only | 26 files, about 16,700 lines | 25 files, 17,085 lines |

The 2026-11-09 Windows count was short: it left out the diagram painters and
some UI files, which is part of why the split looked better than it was.

The two renderers are `src/renderer.cpp` (3,773 lines) and
`src/macos/renderer_mac.cpp` (2,527 lines). The two app controllers are
`src/app.cpp` (6,903 lines) and `src/macos/app_mac.cpp` (1,476 lines).
The margin arithmetic is no longer the only shared piece: both renderers build
a `layout::LayoutInput`, call `layout::LayoutDocument` and paint the same
`layout::DocumentLayout`.

Painting is not the only duplicated drawing: `renderer_pie.cpp`,
`renderer_sequence.cpp`, `renderer_gantt.cpp` and `renderer_state.cpp` build on
the Windows side, and the mac equivalent lives in `mermaid_painter_mac.cpp`.
A diagram painting change is a two-file change today, like a block painting
change is.

### What is left: 2.2, one painter instead of two

The seam itself is done. `platform::TextEngine` and `platform::RenderTarget`
live in `src/platform/seams.h`, the Windows adapters
(`src/windows/text_engine_win.*`, `render_target_win.*`) implement them, the
mac ones (`text_engine_mac.cpp`, `cg_target_mac.h`) do too, and
`tests/seam_conformance_test.cpp` holds both engines to the same grid. The mac
painter is clean: `src/macos/renderer_mac.cpp` names no Core Graphics or Core
Text type at all.

The Windows painter is not clean, but it is close. It names 20 Direct2D and
DirectWrite types (111 before 2026-11-26, 26 after the frame entry points, see
below). No `Renderer` method takes `ID2D1RenderTarget*` any more, and none
mentions an `IDWriteTextLayout`. The three block painters moved first:
`DrawTable` (85 to 77), `DrawCodeBlock` (77 to 68) and `DrawMermaidBlock`
(68 to 42, which also took its arrow head helper with it). Then the three
frame entry points followed (42 to 26, see below): `Render`,
`RenderSourceView` and `PaintSharedOverlays` take `platform::RenderTarget&`.
The caret cache holds a `platform::TextLayoutHandle` now, so its native layout
type left the frame too (26 to 20, 2026-11-27). The 20 that remain are
DirectWrite ownership: the factory, five text formats and the font-family walk.

The diagram painters are single-source now. `src/mermaid/painter.cpp` paints
the flowchart, the pie, the state diagram, the sequence diagram and the gantt
chart on both ports. The two Windows bodies that disagreed with it in three
details were deleted by decision, and the shared painter is authoritative (see
the second entry below).

`tools/check_painter_seam.py` ratchets that number: it fails when the count
rises and asks for a lower baseline when it falls.

### 2026-11-26: the painter leaves the mac directory, two diagrams follow it

`src/macos/mermaid_painter_mac.cpp` never named a Core Graphics or Core Text
type. It is `src/mermaid/painter.cpp` now, moved byte for byte with only the
file comment and the include path changed, and it is the one painter for the
flowchart, the pie and the state diagram on both ports. Windows deleted
`renderer_pie.cpp` and `renderer_state.cpp` and calls
`platform::PaintMermaidDiagram` with a `platform::D2DTarget`, the call the mac
renderer already made. The layout still comes from parse time and rides on the
node, so the paint does no relayout on either side.

Two painters stayed, with the reason for each:

- `renderer_sequence.cpp`. The shared painter draws the autonumber digits at
  12 mermaid units and strokes the activation outline in the palette's
  activation stroke (`#666666`). The Windows body draws the digits at 16 DIPs
  and strokes the activation with its own fill colour. Substituting it would
  change the picture, so it keeps its own body until the two drawings are
  reconciled.
- `renderer_gantt.cpp`. The shared painter sets the section titles in bold and
  the Windows body draws them in the regular weight. Same call: the picture
  would change.

The ratchet did not move, and the reason matters. `tools/check_painter_seam.py`
measures `src/renderer.cpp`, and the four sibling painters were never in that
file: each was its own translation unit. The gated count is the renderer
shell's own Direct2D use (the factories, the brushes, the bitmap), it stays at
42, and the baseline stays at 42 because a lower number would fail the gate.
The duplication that went away is 34 raw names in the two deleted files (21 in
the pie painter, 13 in the state painter). 51 names remain in the sequence and
gantt painters, and they move when those two diagrams do.

### 2026-11-26: the sequence and gantt diagrams follow it, and the shared painter is authoritative

The remaining two Windows painters are deleted. `src/renderer.cpp` sends the
sequence and gantt blocks through `platform::PaintMermaidDiagram` with a
`platform::D2DTarget`, the same call the pie and the state diagram already
made, from the same switch and with the same band origin, block padding and

Where the two Windows bodies disagreed with the shared painter, the repo owner
decided that the shared painter wins. The three differences, now the picture on
both platforms:

- Sequence, autonumber digits: 12 mermaid units, the shared painter's size,
  not the Windows 16 DIP.
- Sequence, activation outline: the palette activation stroke `#666666`, not
  the fill colour the Windows body stroked with.
- Gantt, section titles: bold, as the shared painter sets them, not the
  Windows regular weight.

No golden or capture baseline moved. The geometry goldens are layout output
from the shared engine, and none of the three differences is geometry; the
painting is compared live by the capture parity job, which compares the two
platforms against each other rather than against a stored picture. The painter
ratchet went from 93 to 42 names, in one file instead of three, because the
35 and 16 names the two deleted files carried are gone.

### 2026-11-26: the highlight pass is shared (111 to 85)

The search-match and marker fills were the two helpers typed on Direct2D. They
are now `layout::PaintMatchHighlights` and `layout::PaintMarkerHighlights` in
`src/layout/range_highlights.{h,cpp}`, shared, platform-free, and tested by
`tests/range_highlights_test.cpp` on both platforms. What moved into them is
the policy that used to be copied between the two bodies: the source-to-UTF-16
mapping with its binary search and its linear fallback for unsorted cell maps,
the block clipping, the "nothing touches this block" probe, the current-match
colour, the marker underline, and the batch split into one fill per colour.

The geometry did not move, because only the platform can answer it. The new
seam interface is `platform::TextRangeSource`: the renderer asks for the
rectangles of a UTF-16 range and the platform says where those glyphs ended
up. Windows answers with `platform::DWriteRangeSource`
(`src/windows/text_range_source_win.{h,cpp}`), which carries the per-block
line cache and the `HitTestTextRange` loop that used to sit in `renderer.cpp`,
in the same order with the same clamping, so the same rectangles come out and
no pixel moved. The fills go through `platform::RenderTarget::FillRects`, a
batch method whose default fills one at a time and which `D2DTarget` overrides
with a single brush.

The four paint paths stopped creating their own match and marker brushes, which
is where most of the 26 names went.

### 2026-11-26: the seam can draw a laid out block (the table's glyphs)

`DrawTable` painted its words from the walk record's lines, one `DrawText` per
run. That only worked while a record existed, and the record is the walk's, not
the painter's: a table painted without one drew its washes and its grid and no
words, silently. The seam could not express what the table needed, which is
what a painter actually does with text: draw a block the text engine has
already broken, measured and aligned.

The addition, all in `src/platform/seams.h` and in seam types only:

- `platform::TextLayout`, an interface with `Width()`, `Height()`, `Lines()`
  (the seam's own line records, null for a native layout) and `LineX(line)`
  (where the alignment puts a line inside the column). Plus
  `platform::TextLayoutHandle`, a `shared_ptr<const TextLayout>`.
- `platform::TextAlign` (Left, Center, Right).
- `platform::TextEngine::BuildLayout(runs, maxWidth, align)`, whose default
  builds the portable `detail::LineTextLayout` on top of `MeasureWrapped`, so
  every engine behind the seam answers, including the fake and the SVG ones,
  with no change to their files.
- `platform::RenderTarget::DrawLayout(layout, x, topY, colour)`, whose default
  draws the portable line block run by run through `DrawText`, including the
  underline and strike rules. It is the path a target takes for a block it does
  not recognise, which is how the generic engine's block draws on a real
  target.

The native halves: `DWriteEngine::BuildLayout` builds one `IDWriteTextLayout`
over the runs with per range faces and decorations, and `D2DTarget::DrawLayout`
draws it with `DrawTextLayout` and `D2D1_DRAW_TEXT_OPTIONS_CLIP`, the option
the table always passed. `CoreTextEngine::BuildLayout` keeps the block's
`CTLine`s (the ones `MeasureWrapped` already measured and holds for the hit
tester) with the alignment offset of each, and `CoreGraphicsTarget::DrawLayout`
draws them with `CTLineDraw` inside the block's own clip. Both targets fall
back to the portable path for a block built by another engine.

`DrawTable` now builds its cell block from the shared cell runs
(`layout::TableCellRuns`, the builder the table's own layout uses) at the
column's inner width and alignment, and draws it through the target, so its
glyphs no longer depend on the walk record. The record still fixes the column
split and the row heights. `tests/seam_conformance_test.cpp` grew a block grid:
each engine builds a block, and it is drawn through a real platform target
(Direct2D DC target over a DIB section, Core Graphics bitmap context) into an
offscreen surface whose ink is scanned, so the same assertions run over the
DirectWrite, Core Text and generic engines.

The raw name count in `src/renderer.cpp` did not move (77): the cell layout
this painter still builds for the caret cache is the same DWrite use it had.

### 2026-11-26: the code card draws through the seam (77 to 68)

`DrawCodeBlock` was the last block painter still typed on Direct2D. It created
four to seven solid brushes, filled the rounded card, filled the selection wash
and drew one hand built `IDWriteTextLayout` whose token ranges carried json
drawing effects. It now takes `platform::RenderTarget&` and paints the card
with `FillRoundedRect`, the wash with `FillRect`, and the glyphs through
`DrawLayout`.

Two things had to be true for the pixels not to move. First, the lines come
from the walk record (`layout::LaidBlock::lines`), which is the same block the
display list replay drew under the card: the same breaks, the same CSS line
box, the same per run inks. A caller without a record gets the same lines from
the shared builder, so `layout::CodeBlockRuns` was lifted out of
`LayoutCodeBlock` into `src/layout/code_layout.cpp`, declared next to
`layout::TableCellRuns`, and both readers now ask it. Second, `DrawLayout` had
to paint a whole block in one colour at the time, which was right for a fence
with one ink and wrong for a ```json fence, whose four token colours live on
the runs; those lines were drawn run by run through `DrawText` as a stopgap
that the next step removed (see below). The card's glyph pass is clipped to
its inner box, the box `D2D1_DRAW_TEXT_OPTIONS_CLIP` used to clip to for it.

The one bit of DirectWrite left is the layout the search and marker fills hit
test against and the caret cache keeps (`layoutcache.h` speaks the platform's
own text layout). It is built from the same code format as before, so the
caret and the fills sit where they always did. `DrawMermaidBlock` followed it
(see below); no helper takes `ID2D1RenderTarget*` now.

Step 0 below was right that `layout::AppendRangeRects` can answer the same
rectangles from the shared records. That route stays open and is the one that
retires `TextRangeSource` and `DWriteRangeSource`: it needs `DrawCodeBlock`,
`DrawTable` and the overlay pass to paint from `LaidBlock::lines` first, which
is step 1 and is a bigger change than this one. The pass itself is shared
either way; only the supplier of the rectangles would change.

### 2026-11-26: a laid out block carries its own ink (count unchanged at 68)

`DrawLayout` painted one block in one colour, so a ```json fence, whose four
token inks live on its runs, had to bypass the seam and draw a `DrawText` per
token. That special case is gone. The ink now sits on the run where it
belongs: `platform::GlyphRun` has a `platform::Color color` instead of the four
loose `r`, `g`, `b`, `a` floats, and the default is a transparent colour,
meaning the run has no ink of its own. One helper, `platform::RunInk(run,
fallback)`, answers which ink a run draws in, and every reader asks it:
`DrawLayout`, the display list replay, and the mac renderer's own run pass.
The `color` argument of `DrawLayout` is the fallback for the runs that carry
none, so a block whose runs all leave the default draws exactly as before.

Each target honours the run ink on its own text object, without a second
measure and without changing a glyph position:

- Direct2D: `DWriteEngine::BuildLayout` records every run's UTF-16 range and
  colour on the `DWriteTextLayout` it returns. `D2DTarget::DrawLayout` sets
  the colour as a per range drawing effect (a solid brush, which
  `DrawTextLayout` uses for the glyphs, underline and strike of that range) and
  leaves the ranges with no ink to the brush handed to the call, which is the
  fallback. One layout, one `DrawTextLayout`, the same metrics as before. The
  effects are cleared after the draw so the layout holds no brush between
  frames.
- Core Text: `CoreTextEngine::MeasureWrapped` sets the
  `kCTForegroundColorAttributeName` attribute only on the runs that name a
  colour. A run with none carries no attribute, so `CTLineDraw` paints it in
  the context's fill colour, and `CoreGraphicsTarget::DrawLayout` sets that
  fill to the `color` argument. Same fallback, same `CTLine`s, same breaks.
- The portable default draws each run through `DrawText` in `RunInk(run,
  color)`, which is what a target that does not recognise a block takes.

`tests/seam_conformance_test.cpp` gained the grid's colour rows: a two run
block in red and blue is drawn through the real target and the paper is
scanned per hue, so each colour has to land inside its own run's x range, and
a second draw proves that an uncoloured block still takes the fallback
colour. The existing six block assertions are unchanged.

`Renderer::DrawCodeBlock` now makes one `DrawLayout` call for every fence,
json or not, and the run by run loop is gone. The raw Direct2D and DirectWrite
name count in `src/renderer.cpp` stays at 68: the removal was a seam
simplification, not a new adapter. Layout dump parity and the goldens are
unchanged.

### 2026-11-26: the flowchart draws through the seam (68 to 42)

`DrawMermaidBlock` was the last function that took `ID2D1RenderTarget*`, and
with it went the free `DrawArrowHead` beside it, which only it called. The
body is the same drawing in the seam's terms: the swimlane bands are
`FillRoundedRect` and `StrokeRoundedRect`, the nodes are `FillRoundedRect`,
`FillEllipse`, `FillRect`, `FillPolygon` and their strokes, the solid edges are
one `StrokePolygon` with `closed=false` (the same open figure, so the miter
joints and flat caps of the old path are what the seam strokes), the arrow head
is a three point `FillPolygon` with the same world unit maths, and every label
is a seam block drawn through `DrawLayout` inside a `PushClip` of the box the
old `D2D1_DRAW_TEXT_OPTIONS_CLIP` clipped to.

Two pieces needed care so the pixels stayed put:

- **The label line box.** At the page zoom the labels wore `body_fmt_`, which
  carries a uniform `bodyLineHeight` box, and its baseline is
  `(height - natural) / 2 + ascent`. When the column shrinks a wide diagram the
  old code cloned the format without a line box, so a shrunk diagram's labels
  keep the font's own metrics. `LayOutDiagramLabel` applies exactly that rule
  to the lines `MeasureWrapped` answers, so the unscaled diagram keeps its 1.5em
  box and its struck baseline, and the shrunk one keeps the natural box.
- **The dotted edge.** The seam has no dash stroke style. `StrokeDashedPolyline`
  walks the same polyline with the same pattern (`kMermaidDash`, dash and gap
  in stroke widths, phase carried across the joints), which is the geometry the
  Direct2D custom dash style produced. The one thing the seam cannot say is the
  round dash cap the old stroke style asked for, so each dash now ends flat: a
  sub pixel difference at the tip of each dot, and the only place where this
  conversion is not exact. If that matters, the primitive it needs is a dashed
  stroked polyline (or a cap parameter on `StrokeLine`), not a wider seam.

The arrows never had a curve: every edge is a routed polyline, so no path
geometry primitive was needed. No golden changed, and layout dump, capture and
SVG parity are unaffected because the layout walk reads the same
`mermaid::LaidOutFlowchart` it always did; only the painting moved.

`WINDOWS_BASELINE` drops to 42 in the same commit.

### 2026-11-27: the frame entry points leave Direct2D (42 to 26)

`Renderer::Render`, `Renderer::RenderSourceView` and
`Renderer::PaintSharedOverlays` take `platform::RenderTarget&`. They were the
last three functions typed on `ID2D1RenderTarget*`, and they no longer take an
`IDWriteFactory*` either: the renderer's own `dw_factory_` is the factory the
caret cache builds its layouts with, so the caller does not pass one.

Three things the seam cannot express were handled without reaching for
Direct2D in a new place:

- **The scroll and column offsets.** The seam has no transform. `Render` used
  two `SetTransform` calls and the overlays saved and replaced the transform
  for a pinned table header. The shift now lives on the coordinates:
  `platform::OffsetTarget` (`src/platform/offset_target.h`) is a small
  `RenderTarget` that adds a fixed offset to every call. It is pure seam code,
  and the mac renderer's private `TranslatedTarget` was replaced by it, so the
  two ports share the adapter instead of each keeping one. The pinned header
  is an `OffsetTarget` over the base target with the absolute shift the saved
  transform used to hold.
- **The viewport size.** The seam has no size query, so `Render` and
  `RenderSourceView` take `viewportHeightDip` from the caller that owns the
  window. That is the number `rt->GetSize().height` used to answer, and it
  feeds the same cull band and the same clip. Adding a size query to the seam
  would touch every target and fake for one number the shell already has.
- **The clip antialias mode.** `PushAxisAlignedClip` took `ALIASED`;
  `platform::RenderTarget::PushClip` is `PER_PRIMITIVE` on Direct2D. Both
  clips are axis aligned and sit on the window edge (top offset 0, full width
  and height), so no pixel moves; capture parity is the check.

The other names went with the brushes. The selection wash is one
`FillRects` batch in the palette colour, the inline code chips are
`FillRoundedRect`, the decoded image cache holds the seam's opaque
`BitmapHandle` (released and measured through `ImageHelper`, so the concrete
bitmap stays in the Windows image module), and the two highlight helpers take
a `platform::TextRangeSource` instead of an `IDWriteTextLayout`, which is what
the range seam was for. The source view's selection wash and text draw now use
the same shared range rule and `DrawLayout` as the rendered view.

### 2026-11-27: the caret cache holds a seam handle (26 to 20)

**The caret's questions moved onto the block.** `platform::TextLayout` gained
`LineCount`, `LineHeightAt`, `LineTextRange`, `HitTestPoint` and
`CaretAtOffset`, all in the block's own coordinates and all in UTF-16 code
units, the unit a block speaks (the per line `TextEngine` answers are UTF-8
bytes). The portable block answers from the line records it already carries,
`DWriteTextLayout` passes through to the DirectWrite queries
`src/textlayout_dwrite.cpp` holds, and `CgTextLayout` reads its own CTLines.
The conformance grid asks all three block kinds the same questions, and
`tests/hittest_test.cpp` pins the portable answer the cache path takes.

**The floor is 20, and it is the factory the renderer still owns.** The caret
cache no longer holds a native layout: `layoutcache.h` keeps a
`platform::TextLayoutHandle`, so `BlockLayout` names no platform type, and
`Render`, `DrawCodeBlock`, `DrawTable` and `EnsureSourceLayout` build their
block through `platform::MakeTextLayout` (declared in
`src/windows/text_engine_win.h`, written by the adapter). `DWriteRangeSource`
takes the handle and reads the native object back out of it, and the source
view draws the handle it keeps. Six `IDWriteTextLayout` names left
`renderer.cpp` with that switch (2026-11-27), and the baseline dropped from 26
to 20 in the same commit.

What is left is DirectWrite ownership, not painting: twelve `IDWriteFactory`
(Init and the format setup, the factory parameter every measure and paint entry
point still takes, and the mermaid measure), five `IDWriteTextFormat` (the two
helpers that take one, the format the heading and body pass picks, and
`LineHeightOf`), and three names in the font-family walk
(`IDWriteFontCollection`, `IDWriteFontFamily`, `IDWriteFont`). The next step is
to move the format ownership behind the engine, so an entry point takes a
`platform::TextEngine` instead of a factory, and the mermaid measure takes one
too. The floor comment in `tools/check_painter_seam.py` says the same.

The same day the pie legend got a hairline edge on every swatch
(`src/mermaid/painter.cpp`), in the divider ink so a pale fill is visible on
the light page. The painter is shared, so both ports take it from one file;
no golden moved, because the diagram captures are compared across platforms
and this change is identical on both.

The work, in order, after looking at what the helpers actually need:

0. **The seam primitive already exists.** `layout::AppendRangeRects`
   (`src/layout/selection_rects.h`) turns a source range into rectangles from
   a block's `LaidBlock::lines`, the block's UTF-16-to-source mapping and a
   `platform::TextEngine`. The mac painter uses it for search and marker
   washes, and the Windows overlay pass already uses it for the selection wash
   at the very call site where the two highlight helpers are called. No new
   virtual on `RenderTarget` is needed: the range maths is shared and the
   target only fills rectangles.
1. **The blocker is the per-block text layout.** The Windows highlight helpers
   take an `IDWriteTextLayout*` that the painter builds for itself, plus D2D
   brushes. `layout::code_layout.cpp` already fills `LaidBlock::lines` for
   code blocks and table cells, so the lines exist; the painters have not been
   switched to them. That switch is the real step: point `DrawCodeBlock`,
   `DrawTable` and the overlay pass at the shared lines and the shared mapping
   (`BuildBlockMapping` already builds it), and the helpers lose their DWrite
   parameters one at a time.
2. Then convert each helper to `platform::RenderTarget&` and fill through the
   seam, dropping `FillRangeFromCache` and its brushes. **Done on 2026-11-26
   for the two highlight helpers**, by the `TextRangeSource` route above rather
   than the shared-lines route, because the painters still build their own
   `IDWriteTextLayout`. **`DrawTable` also landed on 2026-11-26**: it takes
   `platform::RenderTarget&`, paints its washes, hairlines, selection fills
   and cell clip through the seam, and draws its glyphs as a seam block
   (`platform::RenderTarget::DrawLayout` of a `platform::TextLayout` the
   engine built), see the block section above. Its cell layout survives only
   for the caret cache. `DrawCodeBlock` and `DrawMermaidBlock` followed, so no
   painter takes a Direct2D target any more, and the frame entry points take
   the seam too (2026-11-27). The caret cache's platform layout type went with
   the seam handle on 2026-11-27 as well, so what is left of 2.2 is the
   DirectWrite factory and format ownership in the Windows renderer, and then
   the merge of the two renderer shells.
3. Move the remaining bodies into shared code, one block type at a time.
4. Delete `renderer_mac.cpp` and its test once the shared painter draws both,
   and keep the seam conformance test as the portable referee.
5. Then the ledger rows that say "renderer, per platform" can be retired, and
   `check_paired_changes.py` can drop the renderer pair.

Until then, the honest description is: one shared core, one shared layout, one
shared controller, and two painters.

## Findings

## Research that shaped the plan

- Scintilla keeps a small portability layer (`Surface`, `Font`) that every
  platform implements, so the core never touches a platform API
  (scintilla.org/Design.html).
- Slack found that building features once per platform produced the same
  bug several times and different behavior on each client. It moved logic
  into one core library and kept UI and OS access native
  (slack.engineering, LibSlack).
- Chromium has an open issue to replace per-platform `RenderText` classes
  with one HarfBuzz plus Skia path, because per-platform text code drifts
  (issues.chromium.org/issues/40078432).
- Zed says abstraction works only if the platform stays behind one API,
  with a direct escape hatch where native depth matters
  (zed.dev/blog/zed-decoded-linux-when).
- Codename One ties each port's support claim to a conformance test that
  must pass, not to a statement.

Not read in full: the Chromium cross-platform UI document and the
Codename One article. Only their search snippets informed this plan.

## Goal

A feature added to the document model, layout or editing behavior reaches
both platforms by construction. Where a platform differs on purpose, the
difference is written down and checked by CI.

  warning annotation.
- A `Parity:` line in the commit message (for example
  `Parity: macOS not affected, layout only on Windows`) silences it and
  records the reason.
- Start as a warning. Promote it to a failure after a month if the
  warnings turn out to be accurate.
- The pair list shrinks as Batches 3 and 4 move code into shared files,
  so the check retires itself.

#### Capture parity (switched on in Batch 1.7)

Both platforms photograph the same named states of the same document and
a compare job checks them. This is the only gate that sees the real
window, so it stays on permanently.

- **Windows capture.** Remove the `if: ${{ false }}` guard on the
  "Capture the states (QA walk)" step in the `build` job. It runs
  `tools/windows-smoke/capture.ps1` on the `windows-2022` runner against
  `tests/fixtures/layout-showcase.md`.
- **Compare job.** Remove the guard on `capture-parity`. It downloads
  `MarkDownIt-window-capture` (mac) and `MarkDownIt-windows-capture`
  and runs `tools/compare_platform_captures.py`.
- **Fix the artifact paths.** The job downloads the mac files to
  `captures/macos` and passes `captures/macos/qa`, and the Windows files
  go to `captures/windows`. The Windows upload step lists
  `build-win/qa/*.png`, so the files land under `qa/`. Check both
  layouts in the first run's "Show what was downloaded" step and correct
  the `--windows` argument if it needs `captures/windows/qa`.
- **Run it as a hard failure from the start**, not advisory. The
  comparison already has thresholds tuned against real captures (see
  `references/macos-qa.md`), and it fails on a dead window, a missing
  state or unreadable ink. An advisory gate was how this one went
  unnoticed.
- **Keep the uploads `if: always()`** so a red run still publishes the
  side by side and overlay pictures for the state that failed.
- **Hold the line on thresholds.** Do not loosen
  `tools/compare_platform_captures.py` to get green. Tighter checks on
  layout go in the layout dump, because fonts differ between Segoe UI and
  SF Pro.
- **Add the states the plan introduces.** The walk covers `doc`, `find`,
  `edit`, `outline`, `source`, `lower`, `end`, `tail`, `tail2`. Each
  batch that adds a visible feature adds its state to both walks and to
  the ledger.

### Pipeline shape after the plan

1. `alignment-static` (seconds). Everything else needs it.
2. `build`, `test-macos`, `build-macos` in parallel. Each runs the full
   test suite, the seam conformance suite, the layout dump, the
   transcripts and the test inventory.
3. Compare jobs on `ubuntu-latest`, needing both platform jobs:
   `svg-parity` (exists), `test-inventory-parity`, `layout-parity`,
   `transcript-parity`.
4. `capture-parity` (on again), needing `build` and `build-macos`,
   plus `oracle` and `verify-export` (exist).

The compare jobs follow the existing `svg-parity` job: download the two
artifacts, run a Python script, upload the diff when it fails.

### Making it bite

- **Push to main triggers CI after the fact.** The repository workflow in
  `AGENTS.md` pushes to main, so a required status check cannot block the
  push. Add `tools/check_alignment.sh` that runs the whole static job
  locally, and call it before every push. It is Python only and runs in
  WSL. It does not start any Windows program.
- **Check the triggers.** Confirm that no `paths` or `paths-ignore` filter
  in `build.yml` skips a platform job when a shared file changes. A shared
  change must run both platform jobs.
- **Failures must say what to do.** Every checker ends with the file to
  edit or the command to regenerate (`python3 tools/update_layout_goldens.py`).
- **Time budget.** The static job and the dumps add well under two
  minutes. The macOS queue, not the new gates, is the slow part.
- **No flaky gates.** The layout dump uses the fake measurer, so no font
  or OS version reaches it. Gates that read real fonts stay advisory.
- **Retire gates.** When Batch 3 finishes, the paired-file advisory for
  renderers goes away. When Batch 4 finishes, the same goes for the
  controllers.

## Risks

- **Windows regression.** Moving the Windows renderer onto shared layout
  can change pixels. Mitigation: one block type per step, capture
  comparison and goldens before and after.
- **Font differences.** Segoe UI and SF Pro wrap differently, so shared
  layout with real fonts will not be byte identical. Goldens use the fake
  measurer for exactly this reason.
- **Performance.** The shared layer must keep the layout cache behavior
  (`src/layoutcache.cpp`). Check with the `markdownit-ui-perf` skill's
  scenarios (find, typing, scroll) before and after Batch 3.
- **Scope creep.** The seams stay narrow. A new platform call goes in only
  when a renderer needs it and both engines can answer it.
- **Capture flakiness.** A screen grab on a hosted runner can return a
  black frame or miss a state. The compare job already fails on a dead
  window, so a bad grab shows as red, not as a silent pass. If it flakes,
  fix the capture (wait for the state announcement in `walk.log`), do not
  retry blindly.
- **Gate noise.** A gate that fails for reasons nobody can act on gets
  ignored. Each gate ships with a unit test and a plain failure message,
  and the advisory ones stay warnings until they have been right for a
  month.
- **Golden churn.** Layout goldens that change on every feature teach
  people to regenerate without looking. Regeneration goes through one
  script and the diff is reviewed.
- **No Linux target.** The portable `textlayout_generic.cpp` exists for
  tests only. This plan does not add a third platform.
