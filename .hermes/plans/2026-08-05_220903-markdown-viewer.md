# MarkDownIt — Native Windows Markdown Viewer (C++) Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.
> Use the `wsl-windows-native-dev` skill for the WSL→Windows build-swap-verify loop.

**Goal:** A native Win32/C++ application that renders markdown files locally on Windows 10 and 11 — no Electron, no .NET runtime, no external dependencies shipped`.

**Architecture:**
A single-window Win32 app using Direct2D/DirectWrite for text/layout rendering and the
`md4c` C library (vendored, MIT-licensed) for markdown parsing. The app registers file associations, accepts a path via command line and drag-and-drop, re-renders on file change (F5), and uses a vertical-scroll client region for long documents.

**Tech Stack:**
- Language: C++17 (MSVC static runtime `/MT` for a zero-dep binary)
- UI: Win32 API + Direct2D 1.1 + DirectWrite (ships in Windows 10/11)
- Markdown parser: `md4c` (vendored at `third_party/md4c/`)
- Build: CMake 3.20+ targeting the Windows 10 SDK (`10.0.19041.0`)
- CI: GitHub Actions `windows-2022` runner, single exe artifact

### Task 3: `dom.h` — a flat node list (the renderer's input)

**Objective:** Define the in-memory representation the renderer consumes. Keep it dead simple: a flat `std::vector<Node>`, not a tree.

**Files:**
- Create: `src/dom.h`

**Step 1: Write `dom.h`**

```cpp
#pragma once
#include <string>
#include <vector>

enum class BlockKind {
    Heading, Paragraph, CodeBlock, List,
    BlockQuote, ThematicBreak, Table,
};
enum class InlineKind {
    Text, Emphasis, Strong, Code,
    Link, Image, LineBreak,
};

struct InlineBlock {
    InlineKind kind;
    std::u32string text;   // UTF-32 for DirectWrite (one code point per char)
    std::string  url;      // for Link/Image
    int  headingLevel = 0; // 0 for non-heading
};

struct Node {
    BlockKind  block;
    int        level = 0;    // heading level 1-6
    std::vector<InlineBlock> children;
    bool       ordered = false;
    std::u32string raw;     // for code blocks
};

struct Document {
    std::vector<Node> nodes;
    std::u32string    title;
};
```

UTF-32 inlines sidestep surrogate-pair bookkeeping — DirectWrite operates on
code points natively.

**Step 2: Commit**

**Verification:** Compiles into an empty translation unit (header-only for now). No target change yet — CI still green.

### Task 4: `parser.cpp` — md4c → `Document`

**Objective:** Drive md4c's SAX callbacks and push into the flat node list.

**Files:**
- Create: `src/parser.h`, `src/parser.cpp`
- Add `src/parser.cpp` to `CMakeLists.txt`

**Step 1: Write `parser.h`**

```cpp
#pragma once
#include "dom.h"
#include <string>

bool ParseMarkdown(const std::string& utf8, Document& out);
```

**Step 2: Write `parser.cpp`**

Implement these `md4c` callbacks (full signatures in `md4c.h`):

- `enter_block` — on `MD_BLOCK_H`/`MD_BLOCK_P`/`MD_BLOCK_CODE`/etc., push a new `Node` into `out.nodes`, record state on a small `std::stack` (heading level, list ordered-ness) stored in a `ParserCtx` passed as `userdata`.
- `leave_block` — pop the stack.
- `enter_span` / `leave_span` — push/pop inline entries onto the current `Node::children`.
- `text_block` — append UTF-8 bytes into the current inline's `text`, converting to UTF-32 via a 4-state UTF-8 decoder.
- `attribute_block` for image/link URLs: collect into the pending inline's `url`.

Translate UTF-8 → UTF-32 inline: keep a tiny inline decoder (no libicu; a 30-line state machine is enough for valid UTF-8 from md4c).

**Step 3: Add to CMake**

```cpp
int APIENTRY wWinMain(HINSTANCE hInst, HINSTANCE, LPWSTR lpCmdLine, int nCmdShow) {
    AppWindow app;
    if (!app.Init(hInst, nCmdShow)) return 1;
    if (lpCmdLine && *lpCmdLine) {
        std::wstring arg = lpCmdLine;
        // Strip surrounding quotes if present.
        if (!arg.empty() && arg.front() == L'"' && arg.back() == L'"')
            arg = arg.substr(1, arg.size()-2);
        app.OpenFile(arg);
    }
    return app.Run();
}
```

**Step 3: `OpenFile` updates the title**

```cpp
void AppWindow::OpenFile(const std::wstring& path) {
    path_ = path;
    std::ifstream f(std::string(path.begin(),path.end()), std::ios::binary);
    std::string utf8((std::istreambuf_iterator<char>(f)), {});

    std::wstring title = L"MarkDownIt - " + path;
    SetWindowTextW(hwnd_, title.c_str());
    InvalidateRect(hwnd_, nullptr, TRUE);
}
```

### Task 11: Inline spans — emphasis, strong, code, links

**Objective:** Render inline formatting (italics, bold, inline code, links).

**Files:** Modify `src/parser.cpp`, `src/renderer.cpp`

**Step 1: Parser span handling**

`md4c` emits `MD_SPAN_EM`, `MD_SPAN_STRONG`, `MD_SPAN_CODE`, `MD_SPAN_A`, `MD_SPAN_IMG`. For each we push/pop a flag onto a small stack that informs the current `InlineBlock`'s potential style. Current `InlineBlock.text` is flat; for v1, attach formatting flags to the `InlineBlock`:

```cpp
struct InlineBlock {
    InlineKind kind;
    std::u32string text;
    std::string url;
    bool        em     = false;
    bool        strong = false;
    bool        code   = false;
};
```

This loses overlapping-style fidelity (e.g. `***foo***` collapses to single emphasis); acceptable for v1.

**Step 2: Renderer span drawing**

DirectWrite's `IDWriteTextLayout::SetDrawingEffects` supports per-range custom drawing. For v1 we sidestep the cost:
- Iterate over the block's `InlineBlock`s.
- Build ONE `IDWriteTextLayout` per `InlineBlock` with the appropriate font weight (Semibold for strong, Italic for em, Consolas for code).
- Track running X within the block; advance after each inline; wrap on word boundary (DirectWrite's layout wraps when the inline's maxWidth is the *block* width minus current X — so use `CreateGdiCompatibleTextLayout` with the proper max width per inline).

Links get `DWRITE_TEXT_RANGE` coloured `#0366d6` using `IDWriteTextLayout::SetDrawingEffect` with a colour brush; clicking (Task 12 optional) not in v1.

**Step 3: Commit**

```bash
git add src/parser.cpp src/renderer.cpp
git commit -m "feat: render emphasis, strong, inline code, links"
```

**Verification (manual):** Markdown with `*italic*`, `**bold**`, `` `code` ``, `[x](url)` renders each with correct styling. Open a captured README from a popular OSS project; eyeball the match vs GitHub.

## Risks / tradeoffs / open questions

- **DirectWrite per-inline text layout** is the cheap escape for v1 (one `IDWriteTextLayout` per inline span) but breaks accurate word wrap across span boundaries (e.g. `"some **bold** text"` becomes three layouts; if "text" doesn't fit after "bold", it wraps awkwardly). Acceptable v1 trade-off; v2 can build a per-block text layout with `IDWriteTextLayout::SetDrawingEffect` over character ranges.
- **Long code blocks / horizontal scroll** are out of scope for v1 (clip with ellipsis). Real horizontal scroll for code blocks is a v2 feature.
- **Tables / images** are not implemented in v1 (Task 3's `BlockKind` lists them but Render doesn't handle them yet). Print a "not supported in v1" placeholder or skip silently. Decision point at Task 10 review.
- **Icon**: v1 ships a placeholder `.ico`. A real designed icon is a separate task.
- **File associations / installer**: manifest declares readiness, but no installer is cut. Users run the exe directly.
